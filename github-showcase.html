Путь дефектаThe life of a defect

Каждый шаг уже был в портфолио, кроме последних двух. Тест находит дефект и остаётся зелёным, пока дефект есть; отчёт его фиксирует; issue превращает запись в баг-репорт; доска собирает всё вместе; релиз подводит итог.

The first steps already existed; the last ones are new. A test finds the defect and stays green while it exists; the report records it; the issue turns the record into a bug report; the board gathers them; a release sums up.

Issues как баг-трекерIssues as a bug tracker

Каждый найденный дефект — отдельный issue в репозитории, где его нашли. Заголовок начинается с ID из отчёта, тело построено как баг-репорт, метки задают серьёзность и область.

Every defect is an issue in the repository that found it. The title starts with the id from the report, the body is a bug report, labels give severity and area.

  • Форма .github/ISSUE_TEMPLATE/bug_report.yml спрашивает те же поля, что у сгенерированных issues.
  • Ссылка ведёт на строку теста, который закрепляет дефект.
  • Исправленный поставщиком дефект закрывается как completed, проблема песочницы — как not planned (DEF-3…5).
  • The form .github/ISSUE_TEMPLATE/bug_report.yml asks for the same fields as the generated issues.
  • A link points at the line of the test that pins the defect.
  • A defect fixed by the vendor is closed as completed; a sandbox problem as not planned (DEF-3…5).

Релизы файлом с описаниемReleases from a notes file

Релиз выпускается коммитом файла с описанием. Workflow Release видит новый файл в .github/releases/, создаёт тег на этом коммите и релиз с файлом в качестве описания. Уже выпущенные версии пропускаются, поэтому перезапуск безопасен.

A release is published by committing its notes. The Release workflow sees a new file in .github/releases/, creates the tag on that commit and the release with the file as its notes. Released versions are skipped, so a re-run is safe.

Описание проходит ревью как код, а личный токен не нужен: хватает GITHUB_TOKEN с contents: write.

Notes are reviewed like code, and no personal token is needed: GITHUB_TOKEN with contents: write is enough. 

# 1. write the notes
.github/releases/v1.1.0.md

# 2. push to main → workflow runs
gh release create v1.1.0 \
  --target "$GITHUB_SHA" \
  --notes-file .github/releases/v1.1.0.md \
  --latest

# 3. sidebar: Releases · v1.1.0 Latest

The README badge opens VS Code in the browser, and the first command from Running it works. android-testing has none: the emulator needs hardware acceleration.

Демо-PR: CI отклоняет изменениеDemo PR: CI rejects a change

PR #6 в python-testing открыт специально и не мержится. Он заменяет кассовое округление на встроенный round(): три строки, линтеры и mypy довольны, но round() для Decimal округляет к чётному. 76 из 77 тестов зелёные; падает тест Hypothesis, сравнивающий сервис с независимым оракулом, и сжимает пример до двух товаров по 0.01 с купоном SAVE25.

PR #6 in python-testing stays open on purpose. It swaps till rounding for the built-in round(): three lines, linters and mypy pass, but round() on a Decimal rounds half to even. 76 of 77 tests stay green; the Hypothesis test that compares the service with an independent oracle fails and shrinks the case to two items at 0.01 with SAVE25.

  • Checks — красная задача и сводка с вердиктом.
  • Аннотация на строке упавшего теста — в Checks и на странице прогона.
  • Комментарий CI — прошло, упало, время, пример; обновляется при каждом пуше.
  • Checks: a red job and a summary with the verdict.
  • Annotation on the line of the failed test, in Checks and on the run page.
  • CI comment: passed, failed, time, example; updated on every push.
